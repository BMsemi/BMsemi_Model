# ZCU106 X2 Runtime

This folder is the board-facing runtime for the ZCU106 bitstream in
`x2_zcu106/deploy`.

The current FPGA core is an AXI DMA connected `AXIS_X2_SIMD` block with eight
32x32 binary X2 instances. It does not store signed INT8 weights directly.
`x2_runtime.py` therefore maps signed INT8 layers into binary passes:

- lower weight bit planes use coefficients `1, 2, 4, ..., 64`
- the sign bit plane uses coefficient `-128`
- signed inputs are represented by positive and negative unsigned passes
- unsigned activations use one pass per bit plane

This is a correctness path for YOLO layers on the current RTL. It is not the
final realtime path because it requires many DMA/program/VMM passes.


## ZCU106/PYNQ Smoke

Copy `x2_zcu106/deploy` and `x2_zcu106/runtime` to a ZCU106 Linux/PYNQ image,
then run:

```bash
cd runtime
python3 demo_x2_scheduler.py --backend pynq --bit ../deploy/zcu106_x2_dma.bit
```

SSH is just the easiest way to copy files and start this script. PYNQ is just
the easiest Python API for DMA buffers and overlay loading. A Vitis bare-metal
or Linux C runtime can use the same packet format without PYNQ.

## New AXI-Lite MVM Core

`axi_x2_mvm_driver.py` is the PS-side runtime for the
`axi_x2_mvm_accel.sv` block. The v0x00020024 overlay contains two independent
32x32 PE arrays named `axi_x2_mvm` and `axi_x2_mvm_1`. Their AXI-Lite windows
are fixed at `0xA0000000` and `0xA0010000`; each PE has its own weight memory,
execution state, TDC state, and 128-bit AXI DDR reader/writer.

Input allocation uses a 16-byte stride for each valid packed 32-bit word,
matching the 128-bit PS memory port. Output allocation is padded to groups of
four INT32 values, matching one 128-bit write response. The single-PE
`run_mvm_batch()` sends up to 32 vectors per hardware launch and pads every
vector independently.

Example on the ZCU106 Linux/PYNQ image after building
`zcu106_axi_x2_mvm.bit`:

```python
import numpy as np
from axi_x2_mvm_driver import DualAxiX2MvmPynq, numpy_mvm_reference

x2 = DualAxiX2MvmPynq("../deploy/zcu106_axi_x2_mvm.bit")
vector = np.array([1, 2, 3], dtype=np.int8)
weights = np.array([[4, 5], [6, 7], [8, 9]], dtype=np.int8)
result = x2.run_mvm(vector, weights)
assert np.array_equal(result, numpy_mvm_reference(vector, weights))
print(result)
print(x2.engines[0].stats().tdc_first_ready_column)
print(x2.engines[1].stats().tdc_pe_completion_time_ps)
```

`DualAxiX2MvmPynq.run_mvm_batch()` accepts up to 64 vectors. It splits the
batch across both arrays, prepares both DDR transactions, starts both PEs, and
then waits for both results. `AxiX2MvmPynq` remains available for direct
control of one named PE.

`stats()` includes the PL TDC timing metadata. Larger absolute column results
have smaller arrival times; `tdc_first_ready_column` and
`tdc_last_ready_column` report the stable completion order while the returned
INT32 array remains in normal column order. `tdc_arrival_spread_ps` reports the
column skew and `tdc_pe_completion_time_ps` is the latest column arrival. The
single-PE driver requires PL version `0x00020022` or newer; the dual-PE driver
requires `0x00020024` or newer. Version `0x00020022` corrected the input reader
to issue one 16-byte AXI transfer per 128-bit HP-port line.

The full compiler runtime uses this driver through `PynqX2Backend`. A packaged
board application is available at `../deploy/zcu106_hybrid_board.zip`; its
`run_on_board.py` executes all 94 compiled Conv2D layers and the complete CPU
fallback graph.

When the board has no Linux/PYNQ image, the same register and DDR path can be
smoke-tested directly through XSCT/JTAG:

```powershell
& 'C:\Vitis\2022.2\bin\xsct.bat' `
  'x2_zcu106\scripts\run_axi_x2_mvm_jtag_smoke.tcl' `
  'C:\fpga_build\yolo26n_axi_x2_mvm_bd\zcu106_axi_x2_mvm.gen\sources_1\bd\zcu106_axi_x2_mvm\ip\zcu106_axi_x2_mvm_psu_0\psu_init.tcl' `
  'x2_zcu106\deploy\zcu106_axi_x2_mvm.bit' `
  'x2_zcu106\deploy\jtag_mvm_smoke_result.txt'
```

The script initializes PS/DDR, programs the PL, executes a known 3x2 MVM, and
requires the physical result `[40, 46]`.

It also accepts a case generated by the compiler. The batch-32 case for the
first YOLO Conv2D tile (`K=27`, `N=16`) was run on the physical ZCU106 and all
512 INT32 results matched NumPy exactly. The test consumed 332 packed input
words, wrote 512 output words, completed in 24,436 PL cycles, and reported no
accelerator error.

For larger JTAG cases, the compiler emits a binary image using the accelerator's
16-byte DDR input stride. The XSCT loader downloads and verifies that image
before starting the accelerator and repairs any individually corrupted JTAG
word before re-verifying. This verification is required: a detected DDR
download mismatch can otherwise look like a MAC arithmetic failure.
